# debug-info.json (major 1)

`debug-info.json` describes one build for a source-level debugger: its files, its POUs, every
variable of every scope with its IEC type, the instance tree, and the statement map. It is a host-side file: nothing in it is linked into the runtime image.

- Schema: [`debug-info.schema.json`](debug-info.schema.json) (JSON Schema draft-07).
- Produced by `compile()` as `CompileResult.debugInfo`; serialise it with `serializeDebugInfo()`
  (`src/backend/debug-info-gen.ts`), which sorts keys so equal inputs give equal bytes.
- It sits beside `debug-map.json` (`DebugMapV2`). Static storage is addressed through
  `debug-map.json` leaves; this file only says where each instance and global starts in them.
- Read it with `readDebugInfo(text, image?)` (exported from the package), which applies the
  version and build-binding rules below.

All names are upper-cased, as the compiler folds identifiers and as `debug-map.json` leaf paths
are written. IEC identifiers are case-insensitive, so a reader compares them that way.

## Versioning

| Field | Meaning |
|---|---|
| `format` | Always `"strucpp-debug-info"`. |
| `major` | `1`. A reader refuses any major it does not support and names both versions. Removing or re-meaning a field is a major bump. |
| `minor` | `1`: adds `pous[].frameLeaves`, `instances.parent` and the probe-build instance table; `localsSlot` is set. Additive changes only. Every object may carry properties the schema does not list; readers ignore what they do not know. |

`debug-map.json`'s own `version: 2` is a separate axis and does not move with this format.

`readDebugInfo` refuses a file whose `format` differs or whose `major` is not `1` with
`UNSUPPORTED_DEBUG_INFO`, `details: {found, supported}` (`found` is `null` when there is no
integer major), and accepts any `minor`.

## The file set

`emitDebugArtifacts(result)` returns the four files every build path writes, so the same inputs
and options give byte-identical files from `compile()`, `strucpp --debug-artifacts <dir>` and the
editor:

| File | Bytes |
|---|---|
| `generated_debug.cpp` | `result.debugTableCpp`. |
| `debug-map.json` | `JSON.stringify(debugMap, null, 2)`, no trailing newline: the editor's serialisation, unchanged. |
| `debug-info.json` | `serializeDebugInfo(debugInfo)`: sorted keys, no whitespace. |
| `defines.h` | `#pragma once`, `// Program MD5` and `#define PROGRAM_MD5 "<md5>"`, each ending in a newline. |

The CLI's `--md5 <hex>` passes the program md5 the editor computes over `program.st` when the
sources given are the editor's per-POU files.

## Build binding

Three artefacts of one build carry the same `buildId`:

| Where | What |
|---|---|
| `debug-info.json` | `build.buildId` (below). |
| `debug-map.json` | One additive top-level key, `"debugInfo": {"file": "debug-info.json", "major": 1, "minor": 1, "buildId": "<hex>"}`. `version` stays `2`; the editor's loader ignores the key. |
| `generated_debug.cpp` | `extern "C" const char strucpp_dbg_build_id[]`, the 64-character hex id, NUL-terminated. Emitted in every build, probes on or off; the runtime resolves it by name. |

`readDebugInfo(text, {md5, buildId})` refuses debug info of another build with `STALE_BUILD`,
`details: {reason, expected, found}`: `reason` is `source` when the md5 differs, else `build`
when the buildId differs. A `null` image `buildId` compares by md5 alone.

## `build`

| Field | Meaning |
|---|---|
| `md5` | Program identity, the value served on the runtime's 0x45 request: the caller's `md5` option verbatim, or else MD5 over the UTF-8 bytes of the user source files concatenated in compile order (for a single `program.st`, the editor's value). `debug-map.json` `md5` is the same value. |
| `buildId` | Build identity, SHA-256 (hex) over the compiler version, the canonical `options`, each source file's path and SHA-256, and each library's name, version and content hash. Computed from inputs, so it is known before code generation. |
| `compiler` | `"strucpp <version>"`. |
| `options` | The compile options that change generated code, with sorted keys. `debugProbes` is always present. |
| `time` | Optional and informational; never part of `buildId` or any compared byte. Not written today. |
| `probes` | `true` for a build compiled with debug probes, `false` otherwise. |

## `files`

One entry per user source file, in compile order. `id` is the index other tables use.

| Field | Meaning |
|---|---|
| `id` | Index of this file. |
| `path` | The file name passed to the compiler. |
| `sha256` | SHA-256 (hex) of the file's exact UTF-8 bytes. |
| `library` | Name of the library the file belongs to, or `null` for a user file. |
| `generated` | `true` when the whole file was generated by a tool. |

## `pous`

One entry per program, function block, function and method of the user source, then one per
library function and function block linked into the build (`CompileResult.linkedPous`), with
`noSource: true`, `noSourceReason: "library"` and no probes; a library function's parameters are
its `locals`. Every linked POU appears. Each property accessor is
a body of its own and is listed as a `method` of its function block named `<property>.GET` or
`<property>.SET` (`P.GET`); its `span` is the `GET ... END_GET` or `SET ... END_SET` block.

| Field | Meaning |
|---|---|
| `id` | Index of this POU. |
| `name` | POU name. |
| `kind` | `program`, `fb`, `function` or `method`. |
| `owner` | For a method, the `id` of its function block; otherwise `null`. |
| `file` | `files[].id` of the declaring file, or `null` for a library POU. |
| `span` | `[startLine, startCol, endLine, endCol]` of the declaration, 1-based, or `null`. |
| `entryProbe` | First probe of the body (the lowest probe ID of this POU), or `null` when the body is empty or has no source. |
| `noSource` | `true` when the POU has no source in this build. |
| `noSourceReason` | `library`, `binary` or `optout` when `noSource` is `true`, else `null`. |
| `cppSymbol` | Mangled C++ symbol of the body, or `null` when not recorded. |
| `generated` | `true` when a `{strucpp generated}` pragma before the POU marks it as generated code. |
| `typeId` | For a program or function block, the `types[].id` describing its instance members; `null` for a function or method. |
| `locals` | Stack-resident variables (see below). |
| `frameLeaves` | The frame's locals table (see [Frames](#frames)), or `null` when the body has no frame: probe-off, a library POU, or an empty body. |

### `locals`

Variables that live in the POU's frame, not in an instance: every variable of a function or a
method, and the `VAR_TEMP` variables of a program or function block.

| Field | Meaning |
|---|---|
| `name` | Variable name. |
| `typeId` | `types[].id` of its type. |
| `kind` | The var block it is declared in (`VAR`, `VAR_INPUT`, `VAR_OUTPUT`, `VAR_IN_OUT`, `VAR_TEMP`, `VAR_INST`). |
| `localsSlot` | Slot of the variable's first leaf in the frame's locals table (`frameLeaves`). `null` probe-off, and for a variable with no readable leaf (a reference, a `STRING(n)` with `n ≠ 254`, an `ArrayView` `VAR_IN_OUT`). |

### `frameLeaves`

Columnar, index = slot. One entry per elementary leaf of the POU's `locals`, in `locals` order,
each variable expanded as the debug-map leaf walk expands static storage (struct fields in
declaration order, array elements in index order, a library FB's interface).

| Field | Meaning |
|---|---|
| `path` | Leaf path inside the frame: `X`, `P.A`, `ARR[1]`. |
| `type` | Type tag name, as `debug-map.json` leaves' `type`; its number is `typeTags[type]`. |
| `size` | Bytes `strucpp_debug_read_at` writes for it. |

## Frames

A probe build links a frame record (`strucpp_dbg_frame`, `debug_probe.hpp`) on every entry of a
probed clone while a session is attached (ADR-001 D3). Two fields carry what a stack walk needs:

- **`pou`** is the body's `entryProbe`: the POU is the `pous[]` entry with that `entryProbe`.
- **`locals`** is `void* const[]`, `frameLeaves.path.length` long: slot `i` is the address of
  leaf `i`, in the live activation (a `VAR_IN_OUT` slot is the referent's address). Read one
  with `strucpp_debug_read_at(locals[i], typeTags[frameLeaves.type[i]], dest)`
  (`debug_dispatch.hpp`, exported with the other `strucpp_debug_*` shims), only while the task
  is parked on that stack. `nullptr` when the POU has no frame leaf.
- **`self`** is the program or FB instance (`this`), or null for a function. It is resolved
  through the instance table, below.

The table is built in the probed clone only, so it costs nothing while no session is attached.
A program's or FB's `VAR_TEMP` is a member of the instance in the generated C++; its slots point
there.

### Instance table (`generated_debug.cpp`, probe builds only)

```c
extern "C" const void* const strucpp_dbg_instances[];  /* index = instances[] index */
extern "C" uint32_t strucpp_dbg_instance_count(void);  /* = instances.path.length */
```

Entry `i` is the address of `instances.path[i]`, or null for an instance the leaf walk could not
address (the build warns, naming it). A frame maps to its instance with no guessing:

1. take the instances whose address equals `self` exactly;
2. keep those whose type is the frame POU's type (for a method or accessor, its owner FB) or
   `extends` it;
3. if more than one remains, take the highest index (the innermost; this needs an FB whose base
   is empty, so it does not arise in practice).

No match means `self` is not a static instance: an FB instance declared in a function's or
method's `VAR`, or reached through a reference. The frame then has no instance path; its
locals still read. A host sorts the table by address once per program load. This replaces the
runtime's interim mapping through debug-map leaf addresses (`debug_agent_leaf_of`), which could
only find the nearest leaf at or above `self`.

## Scopes: where each variable is described

| Scope | Described in |
|---|---|
| Program and FB `VAR`, `VAR_INPUT`, `VAR_OUTPUT`, `VAR_IN_OUT` | `members` of the POU's type, with `section`; values through the instance's `leafBase` |
| `VAR_TEMP`, and every function and method variable | `locals` of the POU; values through the frame (`localsSlot`) |
| `VAR_EXTERNAL` | `externals`, resolved to `globals` |
| `VAR_GLOBAL` | `globals` |

## `probes`

The statement map, columnar: index `i` of every array describes probe ID `i`. Every executable
statement of every POU with source has one probe; compound statements (`IF`, `CASE`, `FOR`,
`WHILE`, `REPEAT`) included. Declarations, comments, blank lines and block ends (`END_IF`,
`ELSE`, `END_PROGRAM`) have none. The table is present in every build; `build.probes` says
whether the probes are planted in the generated code.

| Field | Meaning |
|---|---|
| `pou` | `pous[].id` of the probe's POU. |
| `file` | `files[].id` of the probe's file. |
| `line` | First line of the range, 1-based. |
| `col` | First column of the range, 1-based. |
| `endLine` | Last line of the range. |
| `endCol` | Last column of the range, inclusive. |
| `kind` | `0` statement, `1` loop condition, `2` ELSIF condition; `3` reserved. |
| `flags` | bit 0 generated: the statement starts inside a POU marked `{strucpp generated}` or between `{strucpp generated_begin}` and `{strucpp generated_end}`. Bit 1 library and bit 2 locked are reserved and `0` today. |
| `origin` | Index into `origins`, or `-1`. |

**Ranges.** A simple statement's range is the whole statement, through its `;`, however many
lines it spans; statements sharing a line each have their own range. A compound statement's
range is its header, from the keyword to the end of its condition or selector
(`IF r < lo`, `FOR i := 1 TO 3`). The extra probes are:

| Statement | Probes, in ID order |
|---|---|
| `IF` | `0` on the header, then each `ELSIF`'s `2` on `ELSIF` and its condition |
| `FOR` | `0` on the header (initialisation), `1` on the same header (each test of the bound) |
| `WHILE` | `0` on the header, `1` on the same header (each test of the condition) |
| `REPEAT` | `0` on the `REPEAT` keyword, then the body, then `1` on `UNTIL` and its condition |

**Numbering.** Probe IDs are dense, from 0, assigned in one deterministic walk: source files in
compile order, then POUs by the position of their declaration, then statements in source order.
A POU's probes are therefore one contiguous ID range starting at its `entryProbe`; a method's or
accessor's range follows its function block's own body.

**Stability.** Rebuilding byte-identical sources with identical options gives byte-identical
`probes` and `lines`. Probe IDs are not stable across edits: an added or removed statement
renumbers every later probe. A client holding breakpoints across a rebuild re-resolves them by
`(file sha256, line, column)`, never by ID; an unedited file keeps its `sha256` and the
locations of its statements.

`compile()` also records each probe ID in `CompileResult.lineMap`, under the ST line where the
probe starts (`probeIds`), from the same numbering. The entry also carries the `file`, `stCol`,
`stEndLine` and `stEndCol` of that line's first statement; the map stays keyed on the line alone.
`CompileResult.statements` holds one record per probe ID, in probe order: its file, ST range,
kind and C++ line range in the concatenated `cppCode`. Codegen records both where it emits the
statement, so a line with several statements has one record per statement.

## `lines`

Keyed by `files[].id` (as a string), one key per file: the sorted, distinct lines on which at
least one probe starts. These are the breakpoint-able lines; a client needs nothing else to
show them.

**Breakpoint placement** (F026). A breakpoint requested on line `L` of a file binds as follows:

1. Find the innermost POU whose `span` holds `L` (a method or accessor inside its function
   block). If there is none, the breakpoint is unverified with reason `NO_CODE`.
2. Among that POU's probes, take those starting on a line `>= L`. The breakpoint binds to the
   smallest such line, at its first probe by column, and is verified at that line.
3. If there is none, it is unverified with `NO_CODE`. A breakpoint never moves into another
   POU.

A listed line therefore binds where it was asked; an unlisted line binds to a later line, or not
at all.

## `types`

Each type is described once; variables and members refer to it by `id`.

| Field | Meaning |
|---|---|
| `id` | Index of this type. |
| `kind` | `elementary`, `string`, `array`, `struct`, `fb`, `enum`, `subrange`, `union` or `ref`. A program's instance type is described with kind `fb`; its POU says `program`. |
| `name` | Declared name (`INT`, `MOTOR`, `PCT`), or `null` for an anonymous type such as an inline `ARRAY[..] OF` or an inline enumeration. |
| `members` | For `struct`, `fb` and `union`: the members in declaration order. |
| `dims` | For `array`: `[low, high]` per dimension, outermost first; `null` for a variable-length `*` dimension. |
| `elem` | For `array`: `types[].id` of the element type. |
| `values` | For `enum`: `[name, value]` pairs in declaration order. |
| `length` | For `string`: declared capacity in characters (254 when undeclared). |
| `wide` | For `string`: `true` for WSTRING. |
| `base` | For `subrange` and `enum`: `types[].id` of the base type. For `fb`, the type it `EXTENDS` is in `extends`. |
| `range` | For `subrange`: `[low, high]`. |
| `target` | For `ref`: `types[].id` of the referenced type, or `null` when it is an interface or unknown. |
| `refKind` | For `ref`: `ref_to`, `reference_to`, `pointer_to`, or `interface` for a variable of an interface type. |
| `extends` | For `fb`: `types[].id` of the base function block, or `null`. |
| `opaque` | `true` for a library struct whose fields the library does not export; `members` is then empty. |

### `members`

| Field | Meaning |
|---|---|
| `name` | Member name. |
| `typeId` | `types[].id` of its type. |
| `section` | Var block of an `fb` member (`VAR`, `VAR_INPUT`, `VAR_OUTPUT`, `VAR_IN_OUT`); `null` for a struct or union field. |
| `location` | The `AT` address (`%QW0`), or `null`. |
| `format` | Index into `formats`, or `null`. |

A library function block is a black box: its members are its interface (`VAR_INPUT`,
`VAR_OUTPUT`, `VAR_IN_OUT`), as in `debug-map.json`.

## `instances`

Columnar: index `i` of every array describes one instance. Program instances come first, each
followed depth-first by the function-block instances it contains (members, inherited members,
array elements, and fields of structs), then global function-block instances. `VAR_IN_OUT`
members refer to an instance owned elsewhere and are not walked.

| Field | Meaning |
|---|---|
| `path` | Instance path, as in `debug-map.json` leaf paths: `PROG0`, `PROG0.MOTOR1.PID`, `PROG0.AXES[2]`. Global FB instances use the bare global name. |
| `typeId` | `types[].id` of the instance's type. |
| `parent` | Index of the nearest enclosing program or FB instance (through struct fields and array elements), or `null` for a program or global instance. With the instance table, `strucpp_dbg_instances[i] - strucpp_dbg_instances[parent[i]]` is the instance's byte offset in its parent. |
| `leafBase` | Index in `debug-map.json` `leaves` of the instance's first leaf, or `null` if it has none. A member's leaf is `leafBase` plus its ordinal in the type's leaf order. |
| `leafBaseExt` | First leaf of the instance's sections that `debug-map.json` does not yet cover, appended after every existing leaf (the second leaf pass). `null` until that pass exists. |

## `globals`

| Field | Meaning |
|---|---|
| `name` | Global name. |
| `typeId` | `types[].id` of its type. |
| `location` | The `AT` address, or `null`. |
| `leafBase` | Index in `debug-map.json` `leaves` of its first leaf, or `null`. |

## `externals`

One entry per `VAR_EXTERNAL` declaration.

| Field | Meaning |
|---|---|
| `pou` | `pous[].id` declaring it. |
| `name` | Variable name. |
| `global` | Index into `globals` of the storage it refers to, or `null` if no global of that name exists. |

## `origins`

Graphical-language source references (LD/FBD), referenced from `probes.origin`. They come from
the transpiler's source maps, passed as `compile({sourceOrigins})` or `strucpp --source-origins
<file>`, one per ST file:

```json
{"file": "program.st", "origins": [{"span": [23, 3, 23, 41], "pou": "LD_Main", "kind": "rung", "id": "r0"}]}
```

Every entry is carried unchanged, in input order. A probe references the entry with the smallest
`span` (start line, start column, end line, end column; 1-indexed, inclusive) holding its start in
the same file, else `-1`. ST debugging ignores them. Empty when no map is given.

| Field | Meaning |
|---|---|
| `pou` | Graphical POU name. |
| `kind` | `rung`, `element` or `block`. |
| `id` | The editor's element identifier. |

## `formats`

Per-variable display formatters from declaration attributes, referenced by `members[].format`.
Empty today.

## Deriving ADR-006's state table

The state table (ADR-006 D2.2) is the same instance walk with the leaf walk in a state mode:
`instances` gives every storage-owning instance with its `parent`, `strucpp_dbg_instances` its
address, and the leaf walk (`createLeafWalker`, `src/backend/debug-table-gen.ts`) the members.
What the state mode adds is not emitted yet: library FB locals for every instance (the walk
takes them only for a RETAIN instance today), hidden codegen members, vptr records, and the
per-class `offsetof`/`sizeof` replay with its `static_assert`s.
